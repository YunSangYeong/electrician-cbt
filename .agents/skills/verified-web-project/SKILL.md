# 검증하는 웹 프로젝트 개발

사용자의 목표를 실행 가능한 코드와 증거가 있는 검증 결과로 완성한다. 이 스킬은 개발 절차를 재사용하며, 새로 생성하는 코드·문항이 이전 프로젝트와 완전히 같음을 보장하지 않는다. 동일 산출물이 필요한 경우 검증한 Git 커밋·lockfile·런타임 버전·데이터 파일을 사용한다.

사용자 지시와 상위 지침을 우선한다. 기존 저장소의 AGENTS.md와 적용 가능한 지침을 먼저 읽는다. 이 스킬은 권한·샌드박스·네트워크 정책을 우회하거나 기존 사용자 작업을 덮어쓸 권한을 주지 않는다.

## 1. 목표와 기존 상태 확인

- 현재 저장소, 브랜치, Git 변경 상태, README, package/lockfile, 런타임 버전, 기존 실행·테스트·배포 설정을 먼저 확인한다. 기존 변경을 보존한다.
- 기존 체크아웃을 사용한다. 사용자가 요청하지 않으면 Git worktree를 만들지 않는다.
- 사용자 메시지에서 대상 사용자, 핵심 기능, 데이터, 기기·접근성, 배포 대상과 완료 기준을 추출한다. 결정된 사항은 다시 묻지 않는다.
- 합리적인 기본값은 제안과 함께 실행한다. 진행을 막는 필수 정보만 질문하며, 독립적으로 할 수 있는 작업은 계속한다.
- 새 프로젝트의 기술 선택이 열려 있으면 정적 앱으로 충족되는지 먼저 판단한다. 정적 학습 앱은 React·TypeScript·Vite를 기본 후보로 삼되 기존 기술·사용자 요구를 우선한다. 서버·로그인·유료 API를 임의로 추가하지 않는다.
- 필요한 변수·인증·네트워크 정책은 이름과 상태만 확인한다. 기존 인증으로 필요한 실제 작업을 확인하고, 비밀값을 출력하거나 채팅으로 요구하지 않는다.
- 프로젝트 요구사항과 필수/선택 검증을 짧게 정리한 뒤 구현한다. 양식이 있으면 `references/requirements-template.md`를 참고한다. 파일이 제공되지 않았어도 이 본문의 규칙으로 진행할 수 있다.

## 2. 구현과 유지보수

- 사용자가 요청한 실제 동작을 코드로 구현한다. 계획서나 화면 모형만으로 완료하지 않는다.
- UI, 도메인 로직, 외부·학습 데이터는 분리한다. 읽을 수 있는 구조와 타입을 사용한다.
- 한국어, 모바일·데스크톱, 충분한 문제·보기 글씨, 키보드 접근, 오류 상태와 빈 상태를 요구에 맞게 구현한다.
- 변경이 여러 화면에 해당하면 적용 범위를 명시하고 각각 검증한다. 예: '다음 문제 Space'는 대상 모드마다 구현·확인한다. 한 화면에서의 성공으로 다른 화면도 된다고 보고하지 않는다.
- 단축키는 답안 선택과 포커스, 네이티브 버튼 동작, 입력·선택·편집 영역, IME, 수정키, 길게 누르기, 대화상자를 고려한다. 마지막 문제에서 의도치 않은 제출을 막는다.
- 타이머가 필요한 경우 종료 시각을 저장하고 현재 시각과의 차로 잔여 시간을 계산한다. 새로고침·백그라운드·만료 후 재접속·중복 제출을 처리한다. 기기 시계 변경 등 정적 앱의 한계는 정확히 설명한다.
- 로컬 기록은 저장 실패와 손상에 대응한다. 손상 원본을 자동으로 덮어쓰지 않는다. 데이터 확대 시 기존 ID와 진행 기록의 참조를 보존한다.

## 3. 학습 문제·콘텐츠가 있는 경우

일반 웹 프로젝트에 문항 데이터가 없으면 이 절차는 생략한다.

- 원문 기출, 복원, 자체 제작을 구분한다. 확인되지 않은 출제 연도·회차를 만들지 않는다. 학습 자료 버전은 출제 연도와 구별한다.
- 기출 수록에는 원문 대조, 정답 확인, 출처 URL, 이용 조건 확인이 필요하다. 공개 접근 가능하다는 이유만으로 재배포 권한이 있다고 판단하지 않는다. 무단 대량 복제를 하지 않는다.
- 원문 접근 실패를 '자료가 없다'로 단정하지 않는다. 실제 응답과 검증하지 못한 범위를 기록한다. 출처가 미확인인 문항은 검증 대기로 두고 검수 완료 문제은행에 섞지 않는다.
- 자체 제작은 사용한 공식·개념과 실제로 참조한 자료를 구별한다. AI의 일반 지식으로 작성했으면 이를 명시한다. 직접 확인하지 않은 교재·공식 문서를 근거로 인용하지 않는다.
- 자체 저장소 URL은 작성 위치이며 정답을 입증하는 외부 문헌이 아님을 구별한다.
- 각 문항에는 ID, 과목·단원, 문제, 서로 다른 보기, 정답 번호, 상세 해설, 난이도, 유형, 출처, 검증 상태, 적용 버전과 이용 조건을 저장한다. 해당 없는 연도·회차는 null로 둔다.
- 한 문제에 정답이 하나인지, 조건·단위·근사값·반올림 규칙이 충분한지 검토한다. 해설에는 공식, 단위 변환, 수치 대입, 계산 결과를 쓴다.
- 계산 정답을 생성한 코드와 분리된 식·검증 경로로 재계산한다. 정답 번호와 보기의 대응, 동치 보기, 단위 및 반올림 경계도 확인한다. 생성 결과를 그대로 기대값으로 사용하는 검사는 독립 검증으로 부르지 않는다.
- 정답 수치 검증과 해설 문장 전체 검수, 공식 기준 대조, 전문가 검수를 별개의 상태로 기록한다. 자동 테스트 통과를 전문가 검수나 오류 없음의 보증으로 표현하지 않는다.
- ID, 정규화 본문·보기 중복을 검사하고 의미상 중복은 별도 검토한다. 기존 문항 확대 시 이전 문항의 ID·내용 보존을 확인한다.
- 조건 변형을 많이 생성하면 '유형 수 × 조건 수'와 총 등록 수를 함께 공개한다. 숫자 변형 문항 수를 독립 개념·유형 수 또는 기출 수처럼 보고하지 않는다. 새로운 유형과 수치 변형의 비율은 사용자의 목표에 맞춰 정한다.
- 같은 계산 유형의 변형이 모의시험에 과다 출제되지 않도록 선정 방식을 검토한다. 문항 확대가 과목 분포와 시험 난이도에 미치는 영향을 확인한다.
- 재생성 절차가 있으면 시드, 입력값, 정렬·ID 규칙을 고정한다. 생성 반복 시 결과가 같고 다른 버전 자료를 지우지 않는지 확인한다.
- 법령·공식 출제기준은 실제 확인한 판과 적용 기간만 표시한다. 미대조 자료를 공식 기준에 부합한다고 주장하지 않는다.
- 출처 검수 표가 필요하면 `references/source-review-template.csv`를 사용한다. 기본 문항과 사용자의 로컬 등록 문항 수는 구분한다.

## 4. 검증

- 변경에 적합한 의미 있는 기존 테스트를 실행한다. 새 테스트가 필요하면 실제 실패를 잡는 경계·회귀 시나리오를 추가한다. 구현을 그대로 따라 쓰는 검사나 사소한 수정용 불필요한 테스트는 만들지 않는다.
- 실행한 명령, 종료 코드, 통과·실패·건너뜀 수를 확인한다. 0개 테스트 실행을 성공적인 기능 검증으로 보고하지 않는다.
- 해당 워크플로에 필요한 타입 검사와 production build를 실행한다. 오류를 숨기거나 검사를 완화해서 통과시키지 않는다.
- 앱을 실행하고 대표 기능을 실제 요청 또는 브라우저로 확인한다. PID·열린 포트·HTML 제목만으로 기능 성공을 판정하지 않는다.
- 학습 앱은 시험 시작→답안 변경→새로고침 복원→제출·시간 초과→채점·해설→오답 재학습→기록 저장을 필요한 범위에서 검증한다. 타이머는 가상 시계로 경계도 확인한다.
- PC·모바일 화면에서 문제·보기·패널·입력과 가로 넘침을 확인한다. 기기 에뮬레이션을 실제 기기 검증이라고 부르지 않는다.
- 키보드 기능은 실제 keydown/keyup 입력으로 검증한다. 포커스가 답안 버튼에 남아 있는 경우, 다음 버튼에 있는 경우, 미응답·마지막 문제·대화상자·반복 입력을 확인한다.
- 필요한 검사가 실패하면 원인을 진단하고 수정·재검증한다. 확인된 애플리케이션 결함, 환경 차단, 미실행 검사를 구분한다. 새 변경이나 미해결 문제가 없으면 관련 없는 테스트로 확장하지 않는다.

## 5. Git과 실제 배포 확인

- 커밋 전 의도한 diff와 사용자 변경 보존, 비밀값·불필요한 생성물이 포함되지 않았는지 확인한다. lockfile·재현 가능한 실행 방법을 남긴다.
- 사용자 지시로 저장소 반영이 허용된 경우 커밋하고 적절한 브랜치에 푸시한다. 거부·인증·충돌을 진단하고 무단 force push·권한 우회로 해결하지 않는다. 외부 게시가 허용되지 않았으면 검토 가능한 상태로 준비한다.
- GitHub Pages를 쓸 때 base 경로, main/대상 브랜치, workflow 권한, Pages Source 설정과 산출물을 확인한다. 최초 활성화에 관리자가 필요한 경우 필요한 설정만 안내한다. 불필요한 토큰을 요구하지 않는다.
- '로컬 빌드 성공', 'main 원격 반영', 'CI 검증 성공', '배포 성공', '공개 사이트에서 동작 확인'을 별개로 기록한다.
- 푸시한 정확한 커밋의 Actions 실행을 추적하고 검증 작업·배포 작업 결과와 게시 URL을 확인한다. 이전 커밋의 배포 성공을 새 변경의 성공으로 보고하지 않는다.
- 접근 가능한 경우 실제 공개 페이지와 기능을 점검한다. 네트워크 때문에 직접 확인할 수 없으면 CI 배포 증거와 직접 사이트 검증 불가를 구분한다. 새로고침 안내만으로 배포 실패를 캐시 문제라고 단정하지 않는다.
- 반영되지 않는다는 피드백은 실제 사용 화면·모드, 원격 커밋, 최신 workflow, 게시 경로, 브라우저 캐시, 키보드 포커스를 순서대로 진단한다. 원인이 확정되지 않은 부분은 확정되지 않았다고 보고한다.

## 6. 완료 보고와 인수인계

- 실제 구현 기능, 검증한 커밋, 명령·테스트 수, 배포 실행 링크·상태·주소, 남은 제한과 사용자에게 필요한 조치를 간결하게 보고한다.
- 문제은행이면 실제 등록 수, 유형별 수, 계산 변형의 유형/조건 수, 내부 계산 검증·문장 검토·전문가 검수·공식 기준 대조 상태를 구분한다.
- 구현하지 않았거나 검증하지 않은 기능·출처 확보·배포를 완료로 표현하지 않는다.
- README에는 실행·빌드·테스트·배포, 런타임 버전, 데이터 및 출처 정책과 한계를 남긴다. 필요하면 `references/verification-report-template.md`를 사용한다.
- 반복 작업에 필요한 프로젝트 규칙은 기존 AGENTS.md를 보존하면서 적절한 위치에 기록한다. 이 스킬 자체를 고치거나 설치·계정 전체 등록했다고 주장하지 않는다.
